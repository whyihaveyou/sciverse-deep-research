# P5 上下文预算 + 阶段 checkpoint（O1）

> 承接 @资深产品经理_Lili 委派（O2 门禁落地后，O1 为架构级下一步）。目标：治 10.7M token 上下文漂移的**根因**——让流程不再依赖"单个执行者在同一个无限增长的上下文里顺序跑完全部阶段"。

## 问题根因

SKILL 第 37 行"单执行者约束（关键）"目前是硬绑定：**同一执行者在同一上下文内顺序完成全部阶段**。长综述跑下来，上下文越滚越大（实测 10.7M token），模型工作记忆随上下文膨胀而漂移——正是邱看到的质量问题背后的一层根因。

## 方案：有界上下文阶段单元 + 盘上工件

不推翻单流向，只把"无限同上下文"换成"**有界的阶段单元，由盘上工件连接，任一上下文实例按工件恢复续跑**"。确定性仍由 `.workflow/` 盘上工件（台账、draft、checkpoint 摘要）保证，不靠模型持续记忆。

1. **有界阶段单元**：流程切成阶段一（检索+铸账）→ 阶段二（综合）→ 交付编译。每个单元在**受控上下文预算**内完成；超预算前必须先 checkpoint 落盘，不得带病往下滚。
2. **盘上工件接口**：阶段间状态通过 `.workflow/` 传递——`citation_ledger.json`（已验证）、`draft.md`（键值草稿）、每节台账切片脚手架、单元级 `checkpoint.md`（本单元结论/未决项/衔接点）。工件即接口，不是模型口头记忆。
3. **每阶段预算**：为各阶段设 token 预算上限（分档：检索/综合/编译），超限即触发 checkpoint + 续跑（新上下文只读必需工件，不重演历史）。
4. **checkpoint 续跑**：从盘上工件恢复，新上下文只加载本单元所需工件；恢复时校验工件完整性（台账 validate、draft 键值语法）。
5. **成本足迹**：每阶段记录 token 消耗写入 `checkpoint.md`，可审计、可比对（治成本，也治"跑没跑、算没算清"）。
6. **保留台账/compile 确定性**：数字引用与参考文献仍由 `citation_ledger.py compile` 从同一台账一次铸造；checkpoint/换上下文绝不绕过 validate/compile 直接改编号——确定性由盘上文件保证，因此换上下文后仍可校验。

## SKILL 措辞调整（Phase B 全量）

改写第 37 行"单执行者约束"：
- 删"同一个执行者在**同一上下文内**顺序完成"的强绑定。
- 替换为："阶段单元由盘上工件连接；单个上下文实例可能只覆盖若干单元，**换上下文续跑必须先从盘上工件恢复**；台账/compile 确定性由盘上文件保证，与上下文实例数无关。"
- 保留"不存在编排是别的组件的职责"：续跑仍是读到本 skill 的 agent 按工件恢复，不是平台级编排介入。

## 护栏（Red Team / 防漂移）

- 台账是**单写事实源**：任何阶段单元不得绕过 validate 直接改编号；续跑首动作是 `citation_ledger.py validate`。
- checkpoint 摘要是"交接物，不是事实源"：摘要里的结论若要进正文，必须回到对应工件（台账/切片）核对，禁止凭摘要把模型自述当事实写回。
- 恢复时若工件缺失/已变，停止并报告，不靠记忆补造。
- 预算不当作硬性质量门，只作漂移触发器——超限要么续跑要么缩减范围，不偷偷拉满上下文带病完工。

## 落地节奏

- **Phase A（轻量验证，先做）**：选一个阶段单元（如 dft-kL-demo 的综合段或一次真实检索跑），验证「每阶段预算 + 工件边界 + 收束续跑」三件事真有收益且不破坏 compile/门禁确定性。通过再 Phase B。
- **Phase B（全量）**：改 SKILL 单执行者措辞 + 编排说明 + 工件清单落库；用我们侧同模型(deepseek-v4-flash-0731)同固定 prompt 重跑 spectral 做终验。
